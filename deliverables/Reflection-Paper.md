In Workshops 5–6, I applied that cycle to AuditTrail AI, a dashboard for auditors reviewing invoice anomalies. The narrow first version checks two explicit cases: hourly rates over a $150-per-hour cap and duplicate invoice numbers. I chose deterministic rules because the required checks are clear, repeatable, and explainable. Each invoice shows the line items and the reason it was flagged, while the auditor remains responsible for approving, flagging, or rejecting it. This also helped me be more precise about the word “AI”: this implementation is AI-branded, but its current anomaly engine is rule-based, not a generative model.

AI assistance changed how I approached implementation. I got better results when I specified testable outcomes, such as the four seeded cases and their expected risk levels, or the allowed review statuses and rejection of extra payload fields. I used code and runtime checks to challenge assumptions rather than accepting plausible-looking output. One important example came during deployment: the first CodeBuild run failed because the buildspec depended on an environment variable that was not available. Reading the build logs exposed the cause; correcting the buildspec and rerunning it through AWS produced the ECR image. That experience reinforced that deployment configuration needs the same scrutiny as application code.

Testing also made the project’s boundaries clearer. The API was checked for valid and malformed review requests, unknown invoice IDs, and exact CORS behavior. Browser checks covered the filtered CSV export, notification dropdown, keyboard navigation, visible focus, and retry after a simulated outage. These checks give confidence in the demo workflow, but they do not establish production readiness. The deployed service is public over HTTP, has no authentication, and stores invoices and decisions in memory. It is appropriate for seeded demonstration data only; real financial data would require identity controls, HTTPS, durable storage, and a stronger operating model.

My most valuable lesson is that a successful build is not the same as a successful product. A working endpoint answers whether software runs; user feedback and operational evidence answer whether it helps safely. With more time, I would add a persistent database and audit history, authenticated auditor roles, and a secure HTTPS entry point. I would also measure review time and error rates before and after use rather than claiming savings from assumptions.
